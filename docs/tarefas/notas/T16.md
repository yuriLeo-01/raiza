# T16: executor de perfis via hidraw

Status: ✅ pronto para revisão. Crate novo: `crates/raiza-provider-hid` (id `hid-perfis`).

## O que foi feito

- **`HidProfilesProvider`** (`src/provider.rs`): implementa `raiza_core::Provider`.
  - `HidProfilesProvider::new()` usa o HID do sistema e os diretórios padrão;
    `with_parts(backend, fonte_de_perfis, Timeouts)` injeta tudo (testes).
  - Casa cada perfil com as interfaces hidraw pelo `match` (VID:PID, `bInterfaceNumber`, e
    usage page/usage de **cada** coleção de nível mais alto do descritor de relatório).
  - Id pela regra da arquitetura: `DeviceId::usb(vid, pid, DeviceId::usb_instance(serial, porta,
    portas_do_mesmo_modelo_sem_serial))`, a partir do dispositivo USB pai do hidraw. Conferido no
    hardware desta máquina: o Rapoo sai como `usb:24ae:1423:2607-54L`, igual ao `udev`.
  - **Cabo e dongle:** por perfil, só a conexão presente de menor índice no `match` é aberta e
    anunciada. Ao desplugar a preferida, a seguinte é aberta e anunciada (`DeviceRemoved` da
    primeira, `DeviceAdded` da segunda). Se a preferida não abre (ex.: sem permissão), a
    seguinte assume.
  - **Identificação (pilar 1):** com `identify`, a consulta sai ao abrir e a resposta passa por
    `check_identity` (com repetição até o timeout). Sem confirmação, todas as capacidades saem com
    `writable: false` e `write` devolve `ReadOnly` sem gerar bytes. A identificação se repete a
    cada reconexão (o nó hidraw recriado tem outro `token`, então a conexão é reaberta).
    Se dois perfis servem para o mesmo aparelho, vence o primeiro que confirmar; se nenhum
    confirmar, fica o primeiro, somente leitura.
  - **Perfil `verified: false`:** `write` recusa com `ReadOnly` antes de chamar `build_write`.
  - **Escrita:** `build_write` com o estado em cache mais recente, imediatamente antes de enviar,
    sob o mesmo lock de I/O do aparelho. Depois, `CapabilityChanged` com o novo estado.
  - **Leitura:** pedido (se houver) e resposta com repetição: respostas que `parse_response`
    recusa com `Io` (ID, tamanho ou `expect` diferentes, como o "ocupado" do Rapoo) são
    descartadas até `Timeouts::response` (500 ms). Timeout vira `RaizaError::Io`; o aparelho
    continua listado e a próxima leitura tenta de novo.
  - **Relatórios espontâneos:** leitura sem `request` e com resposta `input`. Uma thread por
    aparelho (só quando o perfil usa input reports) lê o hidraw numa **segunda abertura** (cada fd
    do hidraw recebe a sua cópia dos relatórios) e emite `CapabilityChanged` só quando o valor
    muda. Nada é enviado ao aparelho para isso. `read` de uma espontânea devolve o último valor
    recebido; antes do primeiro, espera até `Timeouts::spontaneous` (4 s).
  - **Tipos de relatório:** `feature` → `send_feature_report`/`get_feature_report` (report ID no
    primeiro byte); `output` → `write`; resposta `input` → próximo input report com aquele ID.
    Report ID `0` (aparelho sem relatórios numerados): o hidraw entrega o input sem o ID, e o
    executor o recoloca antes de chamar `parse_response`.
  - **Hotplug:** monitor do udev no subsistema `hidraw` (sem polling), com debounce de 300 ms.
  - **Perfis:** recarregados quando os arquivos mudam (`notify`, recursivo). Perfil inválido: `warn`
    com o erro de validação, e os outros continuam. Perfil alterado → o aparelho é reaberto e
    reanunciado (`DeviceRemoved` + `DeviceAdded`).
  - **Permissão:** sem acesso ao `/dev/hidrawN`, `RaizaError::Permission` com a dica de instalar
    `packaging/udev/70-raiza.rules`; o aparelho fica de fora e os outros continuam.
- **Camadas injetáveis** (`src/backend.rs`, `src/profiles.rs`): traits `HidBackend`/`HidHandle` e
  `ProfileSource`. Reais: `SystemHid` (udev para listar e vigiar; `hidapi` com o backend
  `linux-native`, em Rust puro, para abrir e conversar) e `DirProfiles`.
- **`descriptor`**: leitor mínimo do descritor de relatório (coleções de nível mais alto).
- **Exemplo** `examples/listar-hid.rs`: lista os hidraw com coleções e o que os perfis enxergam.
- Sem `unsafe`. O `AsyncFd::new` depreciado é usado como no provedor udev (o `register` é `unsafe`).

## Para o líder (integração)

- Registrar no `raizad` como o **primeiro** provedor: `raiza_provider_hid::HidProfilesProvider::new()`.
- Diretórios padrão (`DirProfiles::default_dirs`), do mais prioritário ao menos:
  `$XDG_DATA_HOME/raiza/profiles` (normalmente `~/.local/share/raiza/profiles`) e
  `<$XDG_DATA_DIRS>/raiza/profiles` (`/usr/local/share`, `/usr/share`). O pacote deve instalar o
  `profiles/` do repositório em `/usr/share/raiza/profiles`. Para desenvolvimento, use
  `HidProfilesProvider::with_parts(SystemHid::new(), DirProfiles::new([...]), Timeouts::default())`
  com o `profiles/` do repositório; talvez valha uma variável de ambiente no `raizad`.

## Limitações conhecidas

- Cabo de um mouse e dongle de **outro** mouse do mesmo modelo, juntos: só o cabo aparece (não dá
  para saber que são aparelhos diferentes). Dois dongles iguais aparecem os dois.
- Diretório de perfis que não existe quando o provedor começa a vigiar não é vigiado: criá-lo
  depois exige reiniciar o daemon.
- HID por Bluetooth (hidraw sem USB pai) fica de fora: os perfis só casam VID:PID USB.
- A thread de leitura acorda a cada 1 s para conferir se deve parar (sem tráfego com o aparelho).
- RGB não é lido (formato v1): `read` devolve o último estado escrito.

## Como testar com hardware real

1. Instale a regra udev: `sudo cp packaging/udev/70-raiza.rules /etc/udev/rules.d/`,
   `sudo udevadm control --reload` e replugue o aparelho.
2. `cargo run -p raiza-provider-hid --example listar-hid -- <dir-de-perfis>` lista os hidraw (com
   usage page/usage de cada coleção, útil para o `match`) e os aparelhos com perfil.
3. `RUST_LOG=debug ... -- <dir> --ler` lê cada capacidade (só consultas fixas; nada é escrito).
4. Exemplo seguro, só escuta (sem nenhum envio), para a bateria do Rapoo VT2 pelo dongle
   (status espontâneo `0x07`, veja `docs/tarefas/notas/T17.md`):
   ```json
   {
     "schema": 1, "name": "Rapoo VT2 (só escuta)", "vendor": "Rapoo", "kind": "mouse",
     "verified": false, "authors": ["teste local"],
     "match": { "vendor_id": "24ae", "product_id": "1423", "interface": 1, "usage_page": "ff00", "usage": "000e" },
     "capabilities": { "battery": { "read": { "response": { "type": "input", "report_id": 7, "length": 18,
       "fields": { "percent": { "at": 7 }, "charging": { "at": 6, "mask": 2 } } } } } }
   }
   ```
   Nesta máquina o inventário real achou o Rapoo (`/dev/hidraw3`, interface 1, coleção
   `ff00:000e`), mas a regra udev não está instalada, então a abertura deu `Permission` com a
   dica, como esperado. A leitura da bateria no aparelho fica para o mantenedor.
