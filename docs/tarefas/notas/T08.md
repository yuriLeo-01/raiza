# Notas da tarefa T08: Provedor BlueZ + UPower

## O que foi feito

Crate novo `crates/raiza-provider-bluez`, com dois provedores sobre o D-Bus de **sistema** (`zbus` 5, feature `tokio`):

- **`BluezProvider`** (id `bluez`, `BluezProvider::system()`):
  - só dispositivos com `Paired == true`; id `DeviceId::bluetooth(Address)`;
  - nome: `Alias` → `Name` → endereço; `DeviceKind` pelo `Icon` (`audio-headset`/`audio-headphones` → headset,
    `input-gaming` → gamepad, `input-mouse`, `input-keyboard`, `audio-input-microphone`; o resto → `other`);
  - `Connection { medium: Bluetooth, connected, writable: true }` e `Battery { percent, charging: false }` quando há `Battery1`;
  - `write(Connection(b))`: relê o BlueZ, valida com `DeviceInfo::validate` (pilar 1) e chama `Connect`/`Disconnect`.
    Se já estiver no estado pedido, não chama nada.
- **`UpowerProvider`** (id `upower`, `UpowerProvider::system()`):
  - só `Battery` (somente leitura; `charging = State == 1`); `write` valida e sempre recusa, sem tocar em nada;
  - ignora `PowerSupply == true`, `Type` 1/2 e o `DisplayDevice`;
  - identidade, nesta ordem: `NativePath` do BlueZ (`/org/bluez/.../dev_XX_...`) → `bluetooth`;
    bateria do kernel com pai USB no sysfs → `DeviceId::usb(vid, pid, DeviceId::usb_instance(...))`;
    um MAC no nome (ex.: `hid-aa:bb:...-battery`, HID por Bluetooth) → `bluetooth`; senão ignora com log `debug`.
    **Diferença da ficha:** o USB é tentado antes do MAC solto no nome, porque um receptor USB pode expor um `uniq`
    com cara de MAC. O caso "aponta para o BlueZ" continua vindo primeiro.
- **Camadas injetáveis:** traits `BluezBackend`, `UpowerBackend` (implementações reais `ZbusBluez`, `ZbusUpower`, com
  conexão aberta no primeiro uso) e `UsbResolver` (real: `SysfsUsbResolver`, com raiz configurável para testes).
- **Eventos sem polling:** BlueZ por `InterfacesAdded/Removed` (em `/`) e `PropertiesChanged` (em `/org/bluez`);
  UPower por `DeviceAdded/DeviceRemoved` e `PropertiesChanged` (em `/org/freedesktop/UPower/devices`). A cada sinal
  relevante o backend relê o dispositivo e o provedor compara com o estado conhecido (`tracker.rs`):
  - só valores mudaram → `CapabilityChanged`;
  - mudou a "forma" (nome, tipo ou o conjunto de capacidades, ex.: o BlueZ tira o `Battery1` ao desconectar) →
    **`DeviceAdded` de novo com o dispositivo completo**, que substitui o anterior (mesma semântica do
    `MockProvider::add_device`). **O daemon (T04) precisa tratar `DeviceAdded` de id já conhecido como substituição.**
  - despareado/removido → `DeviceRemoved`.
  - `events()` se inscreve nos sinais antes de tirar o retrato e emite primeiro o que mudou desde o `discover`.
- Serviço ausente (BlueZ/UPower/barramento) → lista vazia e log `info`; o fluxo de eventos termina vazio se nem o
  barramento existir. Falha ao ler um dispositivo do UPower afeta só ele.
- Exemplo `cargo run -p raiza-provider-bluez --example listar` (com `-- --eventos` fica ouvindo os sinais).

## O que ficou de fora

- Pareamento, perfis de áudio e volume (fora de escopo da ficha).
- Registro dos provedores no `raizad` (é do líder). Uso: `BluezProvider::system()` e `UpowerProvider::system()`,
  na prioridade `bluez` (3) e `upower` (4).
- `vendor` no BlueZ fica `None` (o BlueZ não expõe nome de fabricante; dá para derivar do `Modalias` no futuro).

## Validações executadas

- `cargo fmt --all --check`, `cargo clippy --all-targets -- -D warnings` e `cargo test`: passaram (19 testes no crate:
  conectado, desconectado, bateria mudando, bateria do notebook/fonte/`DisplayDevice` ignorados,
  `write(Connection(false))` chama `Disconnect`, serviço ausente, sysfs falso com serial/sem serial/gêmeos).
- Na máquina do mantenedor, com o headset pareado e **desligado**, o exemplo mostrou:
  `bt:DE:1E:59:99:7C:AE  联想Thinkplus-K3 pro  (Headset)` com `Connection { connected: false, writable: true }`.
  O UPower desta máquina não tem baterias de periféricos (só o `DisplayDevice`), então lista 0.

## Como testar com hardware real

1. Ligue o headset Thinkplus K3 Pro e deixe-o conectar.
2. `cargo run -p raiza-provider-bluez --example listar -- --eventos`
3. Confira `connected: true` e a `Battery` (aparece quando o BlueZ expõe `Battery1`, que depende do headset
   e de o `bluetoothd` estar com o plugin de bateria). O UPower também deve listar o headset com o mesmo id `bt:...`.
4. Desligue o headset: deve sair um `DeviceAdded` (sem a bateria) ou `CapabilityChanged` de `Connection`.
