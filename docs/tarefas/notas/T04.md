# Notas da tarefa T04: esqueleto do `raizad`

## O que foi feito

`crates/raizad` virou biblioteca + binário (a biblioteca existe para os testes de integração):

- `src/daemon.rs`: `Daemon`, o núcleo sem D-Bus.
  - Provedores em `Vec<Box<dyn Provider>>`, em ordem de prioridade. O `id()` é lido uma
    vez (pânico ou id repetido: provedor descartado com log).
  - Uma tarefa tokio por provedor: `discover`, depois `events`. Tudo que chama o provedor
    passa por `catch_unwind` (`discover`, `events`, cada `next()` do fluxo, `write`):
    - pânico em `discover` ou ao abrir `events`: provedor desligado, os outros seguem;
    - pânico no fluxo de eventos: provedor desligado e **os dispositivos dele são retirados**
      (o estado dele não é mais confiável; as escritas passam ao próximo dono, se houver);
    - pânico em `write`: `SetCapability` devolve `Error.Io`, o daemon segue;
    - fim normal do fluxo (ex.: udev sem monitor): os dispositivos ficam.
  - Estado: por provedor, o `DeviceInfo` que ele anunciou (com `providers` forçado para o id
    dele). A visão dos clientes é `raiza_core::fuse`; o roteamento é `capability_owner`.
  - Sinais (`Signal`) saem por um canal, emitidos com o estado travado (ordem garantida), a
    partir da diferença entre o fundido antes e depois:
    surgiu → `DeviceAdded`; sumiu → `DeviceRemoved`; só capacidades novas ou com outro valor →
    um `CapabilityChanged` por capacidade; nome/tipo/fabricante mudou ou capacidade perdida →
    `DeviceRemoved` + `DeviceAdded` (o par de atualização de `docs/DBUS.md`).
  - `SetCapability`: dispositivo fundido → `DeviceInfo::validate` → provedor dono → `write`.
    Depois de uma escrita aceita, o cache é atualizado com `Capability::apply` (não depende do
    provedor emitir `CapabilityChanged`) e o valor é salvo.
  - **Atualização** (item 8 e ajuste 1 do líder):
    - `DeviceRemoved` seguido de `DeviceAdded` do mesmo id: depois de um `DeviceRemoved`, o
      daemon olha o próximo evento sem esperar (`now_or_never`). Se for `DeviceAdded` do mesmo
      id, é substituição. O udev enfileira o par junto, então ele chega pronto.
    - `DeviceAdded` sozinho para um id que o provedor já tinha: substituição.
    - Nos dois casos: não duplica, não apaga a configuração e **não reaplica**.
  - **Reaplicação**: quando um provedor anuncia um dispositivo novo para ele (descoberta ou
    hotplug), recebe os valores salvos das capacidades de que é dono. Cada valor é validado de
    novo contra a capacidade atual (pilar 1) e só é enviado se mudaria algo.
- `src/config.rs`: `ConfigStore`, `$XDG_CONFIG_HOME/raiza/config.json` (ou
  `~/.config/raiza/config.json`), gravado de forma atômica a cada escrita. Formato no topo do
  módulo. Salva só estado: DPI, taxa, RGB (modo, cor geral e cores por zona, normalizados),
  volume e mudo. Vibração e conexão não são reaplicadas. Arquivo ilegível é renomeado para
  `config.json.corrompido` e o daemon começa vazio.
- `src/service.rs`: interface `io.github.yurileo01.Raiza1` com `parse_id`/`from_wire`/`to_wire`
  e `forward_signals`, que repassa os `Signal`s ao barramento.
- `src/providers.rs`: **o único lugar** com a lista de provedores, em ordem de prioridade:
  `bluez`, `upower`, `udev` (com comentários marcando a posição de `hid-perfis`, `openrgb`,
  `pipewire` e `evdev`). Para o `PipeWireProvider`, basta inserir
  `Box::new(...)` no lugar do comentário `// 5. pipewire`. Também os dispositivos do `--mock`.
- `src/main.rs`: `raizad [--mock] [--config ARQUIVO]`, log por `RAIZA_LOG` (padrão `info`),
  nome no barramento de sessão (falha clara se outro `raizad` já está no ar),
  desligamento limpo com SIGTERM/SIGINT.

## Testes

- `tests/daemon.rs`: pânico em `discover`, `write` e no fluxo de eventos; validação antes do
  provedor; fusão e roteamento entre dois provedores (incluindo `CapabilityChanged` quando um
  segundo provedor chega); par `DeviceRemoved` + `DeviceAdded` preserva a configuração e não
  reaplica; `DeviceAdded` repetido é substituição; reaplicação ao replugar e na partida.
- `tests/dbus.rs`: a API inteira pelo fio, numa conexão `zbus` ponto a ponto, com o
  `RaizaClient` do core: `Version`, `ListDevices`, `GetDevice`, `SetCapability`, sinais,
  erros nomeados e persistência em disco.
- `src/config.rs`: ida e volta do arquivo, normalização do RGB, arquivo corrompido.

Verificado à mão: `cargo run -p raizad -- --mock` + `busctl --user call ... ListDevices`
devolve os dois dispositivos mock; `SetCapability` com DPI inválido devolve
`dpi: 3210 não é múltiplo do passo 50 a partir de 400`. Sem `--mock`, nesta máquina, o
daemon subiu com `bluez` (1 dispositivo), `upower` (0) e `udev` (7).

## O que ficou de fora / decisões para o líder

- `PipeWireProvider` não registrado (ajuste 2 do líder): entra na integração.
- O daemon não usa `Provider::read` (a API não tem método de leitura direta).
- A detecção do par de atualização depende de o `DeviceAdded` já estar disponível no fluxo
  quando o `DeviceRemoved` é processado. Se um provedor mandar os dois com espera entre eles, o
  par vira remoção + reaparecimento: a configuração continua salva (nunca é apagada numa
  remoção), mas os valores salvos são reaplicados se diferirem do estado atual.
- A configuração é por `DeviceId` (limitação já descrita em `docs/ARQUITETURA.md`).
- Não há sinal para "capacidade removida": nesse caso o daemon usa o par
  `DeviceRemoved` + `DeviceAdded`, como `docs/DBUS.md` permite.

## Como testar com hardware real

```sh
RAIZA_LOG=debug cargo run -p raizad
S=io.github.yurileo01.Raiza; O=/io/github/yurileo01/Raiza; I=io.github.yurileo01.Raiza1
busctl --user call $S $O $I ListDevices
busctl --user monitor $S        # plugue/desplugue um mouse, ligue um headset Bluetooth
busctl --user call $S $O $I SetCapability ss "bt:AA:BB:CC:DD:EE:FF" '{"kind":"connection","value":true}'
```

Para a reaplicação, use um dispositivo com capacidade gravável que tenha estado (ex.: volume,
quando o PipeWire estiver registrado): mude o valor, desconecte, reconecte e veja
`configuração reaplicada` no log e o valor em `~/.config/raiza/config.json`.
