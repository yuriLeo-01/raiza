## O aparelho
- `3151:502f` **não é exclusivo da Akko.** O VID `0x3151` é de uma família de controladoras
  (protocolo "ROYUAN"), e o mesmo VID:PID aparece em vários modelos: Akko 5075 V3 HE (device 2807),
  Akko 5087 V3 HE (2829), Akko MOD007 V5 HE (2839), além de Ajazz AK680 MAX, Ajazz NS67 PRO e
  AttackShark R82PROHE. O modelo exato só se descobre pelo "device ID" que o próprio teclado devolve
  ao comando *identify*.
- No Linux, o do mantenedor diz `iProduct = "Akko Keyboard"`, `bcdDevice 5.06` e 3 interfaces.
- **Modelo confirmado pelo mantenedor (2026-11-26): Akko 5087 V3 HE (Magnetic Switch).**

**Pré-condição de segurança para o perfil:** o *identify* `0x8F` deste teclado deve devolver o id

## Fonte principal: Sharkfin (GPL-3.0, compatível com o Raiza)
[dniminenn/sharkfin](https://github.com/dniminenn/sharkfin): configurador aberto para teclados ROYUAN,
com `docs/PROTOCOL.md` (1185 linhas, commit de 2026-11-23) e `docs/BOARDS.md` (1507 teclados).
Marca cada fato com a evidência: hardware, firmware ou só o código do fabricante. Lista o
`3151:502f` como família **gen2**, com escrita suportada.

- **Transporte:** feature reports de 64 bytes, **report ID 0**, nos dois sentidos, na coleção
  vendor usage page `0xFFFF`, usage `2` (alguns Akko usam usage `1`).
- **Checksum:** `0xFF - (soma & 0xFF)` (complemento de um), sobre os bytes 0..=6 gravado no byte 7
  ("Bit7"), ou sobre 0..=7 gravado no byte 8 ("Bit8", usado em `SET_LEDPARAM`).
- **Identificar:** `0x8F` → `[0x8F, id:u32 LE, …]`. Os GETs ecoam o opcode no byte 0.
- **Iluminação:** `SET_LEDPARAM 0x07` (Bit8) / `GET 0x87`:
  `[op, modo, velocidade, brilho, (opção<<4)|flags, R, G, B, ck8]`. Na gen2, velocidade 0..4
  (0 = mais rápido); brilho direto, 0..4 na maioria. O significado do nibble de flags (cor fixa ×
  arco-íris) **varia por teclado**: a maioria dos Akko tem `7` = arco-íris e `8` = cor fixa.
- **Bateria:** sem comando no teclado; pelo receptor 2.4 GHz, vem no byte 1 da resposta de status
  (`0xF7`). O receptor repassa os outros comandos ao teclado (`0xF6` escolhe o alvo, `0xFC` libera
  a resposta).

## ⚠ Pilar 1: riscos documentados pelo Sharkfin
- **Famílias com opcodes que colidem:** yc500 e gen2 usam os mesmos números para coisas diferentes
  ("uma escrita no endereço errado cai num registrador vivo"). A família tem que vir do *identify*,
  **nunca** do VID:PID. Um perfil só pode escrever depois de confirmar o device ID.
- **Opcodes destrutivos (nunca enviar):** `0xAC` (apaga o chip de flash), `0x2C` (apaga a tela),
  `0x7F` com trailer `55 AA 55 AA` (entra no bootloader USB), `0x30` (bootloader da tela).
- Mesmo PID não significa mesma placa.

## O que falta no formato de perfil (decisão do líder)

> **Resolvido em 2026-11-26** (formato estendido pelo líder): `sum8_inv`, `identify` e o bloqueio dos
> opcodes `AC`/`2C`/`7F`/`30` no VID `3151`, mais o trailer `55 AA 55 AA` em qualquer aparelho. Veja `docs/PERFIS.md`.
1. **Checksum `0xFF - soma`** (o formato tem `sum8`, `sum8_neg` = `0x100 - soma` e `xor8`; falta o
   complemento de um).
2. **Pré-condição de identificação:** o perfil precisa declarar "só escreva se o *identify* `0x8F`
   devolver o device ID X". Hoje o formato só casa por VID:PID, o que **não é seguro** para esta
   família.
3. Os opcodes destrutivos acima devem entrar na lista de bloqueio da validação (primeiro byte do
   relatório), além das sequências ASCII.
